# 인수인계: UI 리디자인 브레인스토밍 (2026-10-22)

새 세션이 가장 먼저 읽을 것은 `CLAUDE.md`이고, 그다음 이 문서다. 어제 문서(`docs/handover-2026-10-21.md`)는 구단 시장·경력·업적 상점 작업, 이 문서는 **그 뒤에 시작한 UI 리디자인 브레인스토밍**을 다룬다.

## 1. 지금 어디까지 왔나

- **코드는 한 줄도 바꾸지 않았다.** 리디자인은 아직 **설계 단계(브레인스토밍)** 이고, `superpowers:brainstorming` 스킬의 HARD-GATE(설계 문서 승인 전에는 제품 코드를 만들지 않는다)가 걸려 있다.
- 지금까지 한 일은 ①현재 화면 기준선 촬영 ②킥루(레퍼런스) 조사 ③사용자와 방향 결정 ④결정 사항을 시안(HTML)으로 확인, 이 네 가지다.
- 다음에 할 일은 §5 참고.

## 3. 내가 제안했고 사용자가 아직 명시적으로 확인하지 않은 것 (제 추측)

- 하단 탭 이름과 나누는 기준: 🏠홈(상태·확인할 일·방 그림·다음 턴 진행) / 📅시즌(일정 타임라인·시즌 계획 요약과 '계획 바꾸기'·다른 팀 성적) / 🧑선수(능력치·장비·시설 업그레이드·내 경력) / 🏆기록(도감·업적·업적 상점·명예의 전당·설정). **탭 구조 자체는 "좋을 것 같다"고 했지만 이름·기준은 시안만 보고 동의한 상태**다.
- PC 패널 폭 약 800px(킥루 값을 참고한 추측).
- 기기의 "동작 줄이기(prefers-reduced-motion)"가 켜져 있으면 움직임을 자동으로 "차분" 수준으로.
- 한 번 직접 고른 테마·글자·움직임이 자동 설정보다 우선하고, 설정에 "자동"으로 되돌리는 항목을 둔다.
- 모바일 팝업(이벤트·턴 결과·대회 결과 등)을 지금의 가운데 카드 대신 **아래에서 올라오는 시트**로 바꾼다. 아직 확인받지 못했다.
- 테마와 글자는 서로 독립(예: 테마 C + 갈무리).
- 하단 고정 바는 큰 버튼 하나("다음 턴 진행") + 작은 버튼 3개로 줄인다.

## 5. 다음에 할 일 (브레인스토밍 절차 이어서)

`superpowers:brainstorming` 스킬은 "질문 한 번에 하나, 이해한 부분은 200~300자로 돌려주기, 시안은 보여 주기" 방식이다. 이미 시안 서버를 써도 된다고 사용자가 허락했다.

아직 안 정한 것(우선순위 순):
1. **긴 화면 구조**: 엔딩 화면 8,479px, 도감 4,775px(카드 39장), 시즌 계획 시트 3,893px, 후반 시즌 결산 3,329px을 어떻게 나눌지. 탭 구조 안에서 접기·단계 나누기로 푼다는 방향만 있고 화면별 설계가 없다.
2. **팝업 방식**: 아래에서 올라오는 시트(§3)로 갈지 확정. 업데이트 로그의 이중 스크롤, 첫 접속 가이드 말풍선(`data-guide` 요소)을 새 구조에서 어떻게 할지.
3. **이벤트·턴 결과·대회 결과·계약·결승 중계·미니게임 같은 연출 화면**을 새 디자인에서 어떻게 감쌀지(안쪽 도트 SVG는 유지).
4. **타이틀 장면**: 첫 장면 반응 받기 → 나머지 3장면 다시 그릴지.
5. **도트 그림 수준**: 아이콘·소품은 쓸 만하고 캐릭터 표정·연속 동작은 한계라고 사용자에게 설명했다. 새 일러스트가 필요하면 AI 이미지 도구/작가(`docs/polish-plan.md`)와 이미지 변환 사이트 안내(`CLAUDE.md` §9) 방식으로.

그다음 절차(스킬 기준):
- 규모는 "프로젝트"라서 **설계 문서**를 쓴다: `docs/superpowers/specs/YYYY-MM-DD-ui-redesign-design.md`(커밋). 의도와 이유, 목표·비목표, 제약, 사용자가 정한 것, 빌더에게 맡기는 것을 담는다.
- **빌더 확인**: 새 서브에이전트에 `brainstorming/builder-check-prompt.md`를 주고 문서를 읽혀서 모호한 점을 찾는다. 질문은 "이미 답한 것 / 사소해서 내가 정할 것 / 사용자만 답할 수 있는 것"으로 나누고, 마지막 것만 한 번에 모아서 사용자에게 묻는다.
- 사용자가 문서를 승인하면 `superpowers:writing-plans`로 구현 계획을 쓴다. **그 전에는 제품 코드(화면·CSS 등)를 만들지 않는다.**

## 6. 일정 추정 (사용자에게 말한 것)

테마 3개 포함 전 화면 리디자인은 **약 7~10 작업일**(하루 4~6시간 기준)로 말했다. 준비 0.5 + 토대(토큰·공통 컴포넌트) 1~1.5 + 핵심 화면 2~3 + 나머지 화면 2~3 + 마감 1. 테마를 3개로 늘려서 하나만 만들 때보다 1~1.5일이 늘었다. 확인 횟수와 방향 변경이 일정을 가장 크게 흔든다.

## 7. 기준선·레퍼런스 자료

- **현재 화면 기준선**: `docs/redesign-baseline.md`(문제점 정리와 재현 방법). 스크린샷 32장은 `.playwright-mcp/baseline/`(git 무시, 로컬 전용)에 있다. 핵심 숫자: 엔딩 8,479px / 도감 4,775px / 시즌 계획 시트 3,893px / 후반 결산 3,329px, 홈 하단 고정 바가 뷰포트의 약 30%.
- **킥루**: `.playwright-mcp/kickru/`(12장, 로컬). 확인한 특징: 밝은 회색 배경 + 흰 둥근 카드 + 파란 포인트, 굵은 고딕, 하단에 고정된 큰 파란 버튼, 생성 과정이 점 4개 단계(뒤로가기 화살표), 하단 탭 5개(홈·반응·시즌·선수·기록), 확인 시트는 위쪽이 둥근 아래 시트(태그 칩·키-값 줄·보조 회색 버튼+주 파란 버튼), 시즌 진행 화면은 월 진행 막대 + 건너뛰기, 시즌 결과는 큰 제목에 파란 숫자 강조 + 키-값 목록, PC는 약 800px 가운데 패널(둥근 모서리·부드러운 그림자)에 양옆 배경만 비움.
- 기존 `docs/design.md`의 킥루 분석(§2)은 로딩 화면과 메뉴만 봐서 한계가 있었다고 적혀 있다. 이번에 게임 안쪽까지 봤으므로 필요하면 기획서에 보충한다.

## 9. 사용자 스타일 메모

- 한국어, 결과는 요약해서 말해 달라는 편이고 "이번 턴에 한 작업" 요약을 매 응답 끝에 붙인다(`CLAUDE.md` §9).
- **시안으로 보여 주는 방식을 매우 좋아한다**("와씨 개좋은데?"). 말로 설명하기보다 시안을 먼저 보여 주고, 둘 이상을 비교할 때는 나란히 놓고, 결과는 직접 열어 눈으로 확인한 뒤 말한다.
- 레퍼런스(킥루)를 정확히 베끼기보다 "참고해서 더 다듬고 꾸미라"는 방향이고, 선택지를 하나로 좁히기보다 **여러 개를 설정으로 고를 수 있게** 하는 걸 선호한다(테마·글자·움직임).
- 솔직한 한계 설명을 허용하고 오히려 정확한 설명을 원한다(도트 그림 수준 질문에 한계를 말했을 때 좋은 반응).
