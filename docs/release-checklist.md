# 푸시 체크리스트 (푸시할 때마다 무조건 끝까지)

사용자 지시(2026-10-22): **푸시할 때는 노션 작성, 기획서 갱신, 배포 결과 확인까지 전부 한다.** "푸시해"라는 말은 이 체크리스트 전체를 뜻한다. 푸시는 사용자가 요청할 때만 한다(`CLAUDE.md` §9). 항목을 못 했으면 이유와 함께 보고에 "미수행"으로 쓴다.

## 1. 푸시 전

- [ ] `data/updates.json`에 마지막 푸시 이후의 **인게임 변경**이 다 들어 있는지 확인한다(날짜별 항목 하나, 같은 날은 그 날짜 `items`에 이어 붙임, 해요체, md·노션·테스트·리팩터링은 쓰지 않음).
- [ ] `npx tsc --noEmit`, `npm test`, `npm run build` 통과. 실패하면 푸시하지 않는다(실패 출력을 그대로 보고).
- [ ] `git status`로 의도하지 않은 파일(큰 이미지, 비밀 키)이 안 들어갔는지 본다. API 키는 어디에도 적지 않는다(`git grep`으로 확인).
- [ ] 푸시할 커밋 목록을 `git log --oneline origin/master..HEAD`로 확인한다(요약에 쓴다).

## 2. 푸시

- [ ] `git push origin master`, 결과(`이전해시..새해시`)를 기록한다.

## 3. 배포 결과 확인 (푸시 직후)

배포 주소: **https://paintochamps.tmdrl8336.workers.dev/** (Cloudflare, `master` 푸시 자동 배포).

1. 방금 푸시한 코드를 로컬에서 `npm run build`로 빌드한다(푸시 전에 이미 했다면 그 이후 `src/`가 안 바뀌었는지 확인).
2. 배포본의 번들 해시와 로컬 빌드의 해시를 비교한다. **같아야 최신이 배포된 것이다.**
   ```bash
   curl -s https://paintochamps.tmdrl8336.workers.dev/ | grep -o "index-[A-Za-z0-9_-]*\.js"
   grep -o "index-[A-Za-z0-9_-]*\.js" dist/index.html
   ```
3. 해시가 다르면 배포가 끝나기 전일 수 있으니 1~2분 간격으로 몇 번(최대 10분) 다시 확인한다. 계속 다르면 Cloudflare 대시보드(빌드 로그)를 사용자에게 확인해 달라고 한다. 확인 못 하면 "배포 미확인"으로 보고한다.
4. 해시가 같으면 배포본을 한 번 열어(Playwright 또는 `curl`) 이번 변경이 실제로 보이는지 본다(예: 바뀐 문구가 번들에 있는지 `curl -s <번들 URL> | grep -c "문구"`, 또는 화면 스크린샷).
5. 결과(HTTP 상태, 해시 일치 여부, 확인한 변경)를 보고한다.

## 4. 노션 작성 (푸시한 내용 전부)

노션 메인: `3f9953f3dde981bca030d3fa7fcde6c1`. 도구를 쓸 때는 **인자를 `raw` 같은 한 덩어리로 감싸지 말고 `parent`·`pages`·`page_id`·`command` 등 각 파라미터로 따로** 넘긴다(감싸면 JSON 파싱 오류가 난다). DB에 쓰기 전에는 항상 먼저 fetch해서 속성 이름을 확인한다.

- [ ] **작업일지**(`collection://bc8a35b8-5794-4078-8728-6756aba7486f`): 푸시 단위로 한 건. 속성: 제목, 날짜, 분류(기획·개발·디자인·밸런스·문서·환경설정), 한 일, 다음 할 일, (소요시간). 푸시 해시와 테스트 개수를 넣는다. 같은 날 앞서 만든 항목이 있으면 새로 만들지 말고 보강한다.
- [ ] **트러블슈팅**(`collection://5cf771c1-8c53-4e11-b0fa-caabfd77f3b4`): 이번 작업에서 막혔다가 푸는 데 시간이 든 문제마다 한 건(증상·원인·해결·배운 점, 영역: 기획·엔진·UI·빌드·환경·문서·도구·밸런스, 상태). 원인을 확인하지 못했으면 그렇게 쓴다. 문제가 없었으면 "없음"으로 보고한다.
- [ ] **메인 페이지**: 테스트 개수, 진행 단계, 구현 결과 요약 표, 남은 작업 체크리스트, 완료 내역(날짜·푸시 해시)을 이번 변경에 맞게 갱신한다(`update_content`로 최소 수정).

## 5. 노션 기획서 갱신

기획서 페이지: `3f9953f3dde981b2b00fffa5e2906701`(저장소의 `docs/design.md` 전문과 같은 내용). 푸시한 변경 중 **규칙·화면·수치·결정**이 바뀐 곳을 기획서에 반영한다.

- [ ] 바뀐 규칙·화면이 있으면 해당 절을 고친다. `docs/design.md`도 같은 내용으로 함께 고친다(둘이 어긋나지 않게).
- [ ] 바뀐 게 없는 푸시(문서·테스트만)면 기획서 맨 아래 '갱신 이력'에 `날짜 · 푸시 해시 · 변경 없음(이유)` 한 줄을 남긴다. "갱신했다"고 보고하려면 실제로 페이지를 수정했어야 한다.
- 별도 기획서 하위 페이지(해외 리그, 돈 소비처, 경력·구단 시장 등)가 바뀐 기능과 관련 있으면 그 페이지도 고친다.
